# Создание LIFT, соответствующего требованиям

Данное руководство предназначено для всех, кто разрабатывает _экспортер_ LIFT: код на любом языке программирования, преобразующий модель данных другого приложения в формат LIFT 0.13. `sil-lift` выполняет в этой работе две функции:

- модуль проверки соответствия, который сравнивает выходные данные как со схемой, так и с семантикой, которую схема не может выразить;
- справочник по формам и правилам оформления текста, которым должен соответствовать конечный результат.

Писать LIFT гораздо проще, чем его анализировать: экспортер генерирует только подмножество конструкций, которые создает его собственная модель, и никогда не сталкивается с опциональностью полной спецификации. Самое сложное — это детали (сопутствующий элемент `.lift-ranges`, текст для каждой системы письма, стабильные идентификаторы и экранирование XML), и именно их и выявляют приведенные ниже проверки.

## Пакеты с застежкой-молнией

LIFT обычно переносится в виде одного файла `.zip`; программы FieldWorks и The Combine импортируют и экспортируют данные именно таким образом. `sil-lift` напрямую считывает и записывает сжатые пакеты в любом из двух форматов, используемых в экосистеме: либо файлы находятся в корневом каталоге архива, либо вложены в одну папку верхнего уровня.

### Считывание содержимого упаковки

Команда `sil_lift.load("package.zip")` распаковывает файл в временный каталог, находит единственный файл `.lift` и загружает его (сопутствующие файлы и мультимедиа обрабатываются как обычно).

- Команды CLI `validate`, `stats`, `check-media` и `export` также принимают путь к файлу `.zip`, поэтому приведенный ниже скрипт запускается для пакета в том виде, в котором он есть.
- `stats` и `export`, а также извлечь только файл `.lift`, а не весь пакет. Они остаются недорогими в случае с медиа-насыщенным файлом, а ограничение на извлечение распространяется только на файл `.lift`, а не на всё, что находится рядом с ним.
- Максимальный размер извлечения ограничен 10 ГиБ и 100 000 элементов. Пакет, превышающий любой из этих пределов, отклоняется с ошибкой `LiftParseError`, равно как и тот, пути к элементам которого выходят за пределы каталога извлечения.

### Создание пакета

`Lexicon.save_zip("out.zip", wrap_folder="MyDict")` упаковывает файл `.lift`, его файлы `.lift-ranges`, а также все остальные файлы из исходной папки (media, `WritingSystems/`, `consent/`, ...) в архив ZIP.

- По умолчанию `wrap_folder` — это папка верхнего уровня, названная в соответствии с именем ZIP-архива (согласно соглашению об импорте FieldWorks/Combine); для создания плоского архива передайте значение `False`.
- Записи, содержание которых изменилось после загрузки, при выходе помечаются новым значением `dateModified`, точно так же, как и при вызове `save()`.
  - Пакет — это то, на основе чего происходит сверка импортирующим инструментом, поэтому устаревшая дата в нём приведёт к тому, что обновлённый лексикон будет выглядеть как неизменённый.
  - Она принимает те же параметры `stamp=` и `when=`, что и функция `save()`; см. [Как наносится отметка](../fidelity.md#how-the-stamp-is-applied).

Файлы `.lift` и `.lift-ranges` сохраняют точность воспроизведения на уровне байтов внутри пакета; сам контейнер zip не обеспечивает точность воспроизведения на уровне байтов.

## Проверить выходные данные в качестве контрольного критерия соответствия

Укажите `sil-lift validate` на файл `.lift`. Он запускает RELAX NG как для файла `.lift`, так и для сопутствующего файла `.lift-ranges`, а также выполняет семантические проверки, которые не могут быть выражены с помощью грамматики:

- незавершенные ссылки на `relation`/`variant`;
- дубликаты GUID;
- целостность отношений «элемент-диапазон» и «родительский элемент»;
- значения атрибутов и грамматической информации, не определённые в их диапазоне;
- Ссылки в заголовке `range/@href`, для которых не найдены соответствующие элементы.

Для CI: в случае любой ошибки выдавать результаты в машиночитаемом формате:

```
sil-lift validate export.lift --strict --no-check-media --format json
```

- Параметр `--strict` приводит к сбою выполнения даже при появлении предупреждений (а не только ошибок).
- `--no-check-media` пропускает проверку наличия медиафайлов в файловой системе, поскольку результаты проверки `missing-media` являются ложными срабатываниями, если аудио- и фотофайлы в CI находятся не в той же папке, что и файл `.lift`.
- `--format json` выводит один объект JSON (`{"problems": [...], "summary": {...}}`) вместо текста, понятного человеку; его коды завершения и схема представляют собой поддерживаемый интерфейс, на который распространяется спецификация SemVer (см. [руководство по командной строке](cli.md)).
- `--allow CODE[,CODE...]` (повторяемый параметр) позволяет избежать сбоя выполнения из-за допустимого кода, такого как `uri-not-rfc` в FLEx. Его результаты печатаются, но не подсчитываются.
- `--require-ids` дополнительно выдает ошибку при обнаружении записей, в которых отсутствует `guid`, или при обнаружении элементов, в которых отсутствует `id`; это полезно в тех случаях, когда при последующем повторном импорте необходимо обновить данные, а не дублировать их.

### Защита от незаметной потери данных

«Скрытая потеря данных» — это тип сбоя, при котором экспорт в формат CSV без форматирования приводит к потере данных. Чтобы этого избежать, выполните запрос `stats --format json` для вашей исходной модели:

```
sil-lift stats export.lift --format json
```

В нём приводятся данные о количестве «записей», «значений», «примеров», «ссылок на мультимедиа», «языков», а также «характеристик» для каждого названия.

### Запуск gate без инструментария Python

В рамках непрерывной интеграции (CI) проекта на TypeScript или C# эту же проверку можно выполнить без установки Python с помощью встроенного GitHub Action:

```yaml
- uses: sillsdev/python-sil-lift@v0.1.0
  with:
    path: export.lift
    strict: "true"
    no-check-media: "true"
    allow: "uri-not-rfc"
    format: json
```

или образ контейнера, скомпилированный на основе файла `Dockerfile` из репозитория:

```
docker build -t sil-lift .
docker run --rm -v "$PWD:/work" -w /work sil-lift validate export.lift --strict
```

## Сопутствующий элемент `.lift-ranges`

Контролируемые словари (части речи, семантические домены и любые другие наборы значений, связанные с признаками) хранятся в отдельном файле `.lift-ranges`, на который есть ссылка в файле `<header>`:

```xml
<header>
  <ranges>
    <range id="grammatical-info" href="mydict.lift-ranges"/>
    <range id="semantic-domain-ddp4" href="mydict.lift-ranges"/>
  </ranges>
</header>
```

В справочнике приводится полное определение каждого диапазона. Значения представляют собой `<range-element>`; `parent` формирует иерархию; `label` / `abbrev` / `description` являются мультитекстами:

```xml
<?xml version="1.0" encoding="UTF-8"?>
<lift-ranges>
  <range id="grammatical-info">
    <range-element id="Noun">
      <label><form lang="en"><text>существительное</text></form></label>
      <abbrev><form lang="en"><text>существительное</text></form></abbrev>
    </range-element>
  </range>
  <range id="semantic-domain-ddp4">
    <range-element id="1.6.1.2">
      <label><form lang="en"><text>Птица</text></form></label>
    </range-element>
  </range>
</lift-ranges>
```

Затем в записи происходит ссылка на значение по идентификатору: часть речи значения — `<grammatical-info value="Noun"/>`, а семантическая область — `<trait name="semantic-domain-ddp4" value="1.6.1.2"/>`. Команда `sil-lift validate` проверяет эти ссылки, поэтому укажите диапазоны, которые фактически используются в ваших данных:

- значение, которое не определено в данном диапазоне, вызывает предупреждение `undefined-range-value`;
- Если `parent` не является идентификатором ровесника, это приводит к ошибке `range-parent`.

Эти сравнения выполнены с учетом нормализации NFC, поэтому идентификатор и значение или `parent`, на которое он ссылается, могут различаться по нормализации Unicode. Это не ошибка, а предупреждение о «несоответствии нормализации». Тем не менее, если возможно, используйте единый способ нормализации: потребители, сравнивающие исходные строки, не смогут разрешить эти ссылки. См. также [Диапазоны и носители](folder-media.md).

Если вы создаете экспорт на Python, функции `Lexicon.add_ranges_file()`, `RangesFile.add_range()` и `Range.add_element()` автоматически формируют сопутствующий объект и добавляют ссылки на заголовки; `open_writer(..., ranges=...)` выполняет то же самое для потокового пути.

## Текст и несколько текстов

Каждая строка на одном из человеческих языков в LIFT представляет собой _мультитекст_: по одному `<form>` для каждой системы письма, каждая из которых содержит `<text>`:

```xml
<lexical-unit>
  <form lang="seh"><text>kanga</text></form>
  <form lang="pt"><text>курица</text></form>
</lexical-unit>
```

Модель, в которой строки индексируются по коду языка (тип `MultiString`, `Record<code, string>`, `dict[str, str]`), отображается на эту модель в соотношении «один к одному»: каждая запись по ключу преобразуется в один объект `<form lang="…">`. В одном мультитексте допускается не более одной формы на каждый язык; в противном случае `sil-lift` выдает предупреждение `duplicate-form-lang`.

Экранирование XML — это единственная часть, в которой действительно важно соблюдать точность:

- в тексте элемента символы `&`, `<`, and `>` должны быть экранированы (`&amp;`, `&lt;`, `&gt;`);
- В значениях атрибутов символ кавычки также необходимо экранировать.

Автор `sil-lift` строго следует этим правилам и никогда не изменяет пробелы внутри `<text>`: он не добавляет там отступов, поскольку это привело бы к повреждению лексических данных. Чтобы сохранить исходный вид вывода, используйте библиотеку XML для экранирования и оставьте содержимое `<text>` без изменений, байт за байтом, так как оно представлено в исходном коде.
