# سطر الأوامر

يؤدي تثبيت الحزمة (`pip install sil-lift`) أيضًا إلى تثبيت الأمر `sil-lift` — وهي أداة مدعومة تتماشى مع روح LiftTools وتأتي مرفقة مع الحزمة (كما أنها، بالنسبة لـ `validate`، تمثل مثالاً عمليًّا على واجهة برمجة تطبيقات المكتبة).

```
sil-lift validate PATH [--format {text,json}] [--strict] [--no-check-media] [--allow CODE[,CODE...]]...
                  [--require-ids]
                                           جميع المشكلات، مع الإشارة إلى الملف/المدخل/السطر؛ الخروج 1 في حالة وجود أخطاء
sil-lift stats PATH [--format {text,json}]
                                           عدد المدخلات/المعاني/اللغات (بشكل متواصل؛ أي حجم)
sil-lift sort PATH [-o OUT]               نسخة مرتبة بشكل قياسي وجاهزة للمقارنة (الافتراضي: في المكان نفسه)
sil-lift check-media PATH                 تقرير عن الوسائط المفقودة، والمكتوبة بشكل خاطئ، واليتيمة؛ الخروج 1 في حالة وجود وسائط مفقودة أو مكتوبة بشكل خاطئ
sil-lift export PATH [-o OUT] [--langs L] [--tsv]
                                           صف واحد لكل معنى فرعي (تم تسطيح المعاني الفرعية) إلى CSV/TSV (بشكل متواصل)
```

خيارات `validate`:

- تقوم الخيار `--format json` بكتابة كائن JSON واحد إلى stdout (ولا شيء غير ذلك) لاستخدامه في عمليات التكامل المستمر (CI) والأتمتة؛ انظر المخطط في المثال أدناه.
- يعامل الخيار `--strict` التحذيرات كأخطاء، ويُخرج القيمة 1 في حالة العثور على أي منها — استخدمه لضمان أن عملية البناء لا تتضمن أي تحذيرات على الإطلاق، بدلاً من الاكتفاء بالأخطاء وحدها.
- تتخطى الخيار `--no-check-media` عملية فحص وجود الوسائط في نظام الملفات، مما يؤدي إلى إخفاء النتائج المتعلقة بـ `missing-media` و`media-href-mismatch`. يُعد هذا مفيدًا عند التحقق من صحة ملف تصدير تم إنشاؤه حديثًا، حيث توجد ملفات الصوت/الصور الخاصة به في مكان آخر وليس في نفس المجلد.
- `--allow CODE[,CODE...]` (قابل للتكرار) يعرض نتائج الرموز المحددة، لكنه يستبعدها من قرار النجاح أو الفشل. وينطبق ذلك على الأخطاء والتحذيرات على حد سواء، لذا فإن التحذير المسموح به لا يؤدي إلى تفعيل الخيار `--strict` أيضًا. يُجمِّع سطر الملخص النتائج المسموح بها لكل رمز؛ بينما تُقدِّم الخاصية `allowed` في ملخص JSON إجمالي هذه النتائج. يتم تجاهل الرمز الذي لا يظهر أبدًا، لذا تظل قائمة السماح تعمل حتى بعد سحب الفحص.
- كما أن `--require-ids` تُسفر عن فشل (خطأ `missing-id`) في حالة أي إدخال يفتقر إلى `guid` أو أي معنى يفتقر إلى `id` — وهو أكثر صرامة من LIFT، وذلك بالنسبة لسير العمل التي تعيد الاستيراد باستخدام معرّف ثابت.

عند تمرير `-` كمسار، يتم قراءة المستند من المدخل القياسي (stdin). لا يحتوي المستند المُمرَّر عبر الأنابيب على مجلد، لذا لا يتم تحديد موقع الملف المصاحب له `.lift-ranges` والوسائط.

كما تقبل `stats` الخيار `--format json`، حيث تُخرج الأعداد في شكل كائن JSON واحد.

!!! note
    تُعد رموز الخروج الخاصة بـ `validate` ومخطط `--format json` واجهة أتمتة مدعومة: حيث يخضع كلاهما للاختبارات ولا يتغيران إلا وفقًا لمعايير SemVer.

تقوم الأداة `sort` بإعادة كتابة ملف `.lift` فقط؛ أما الملفات المصاحبة `.lift-ranges` فتُترك كما هي
(يمكن فرزها بشكل منفصل باستخدام واجهة برمجة التطبيقات `RangesFile`).

تقبل الأوامر `validate` و`stats` و`check-media` و`export` أيضًا حزمة LIFT مضغوطة (ملف `.zip` بأي من الترتيبين — الملفات في جذر الأرشيف، أو متداخلة ضمن مجلد واحد من المستوى الأعلى)؛ حيث يتم استخراجها إلى دليل مؤقت ثم يتم حذفها عند انتهاء تنفيذ الأمر. تستخرج أوامر البث `stats` و`export` ملف `.lift` نفسه فقط، لذا فإنها لا تستهلك موارد كثيرة عند التعامل مع الحزم التي تحتوي على ملفات وسائط كثيرة؛ أما `validate` و`check-media` فتحتاجان إلى المجلد بأكمله وتستخرجان محتوياته بالكامل.

أمثلة:

```
$ sil-lift validate dictionary.lift
خطأ [dangling-ref] dictionary.lift:88 (المدخل apu): المرجع 'nope' لا يتطابق مع أي معرّف مدخل/معرّف فريد (GUID) أو معرّف معنى
تحذير [uri-not-rfc] dictionary.lift:6: <range href='file://C:/...'>: استخدام حرف محرك أقراص Windows كمرجع URI (بأسلوب FLEx file://C:/)
خطأ واحد، تحذير واحد

$ sil-lift validate dictionary.lift --format json
{
  "problems": [
    {
      "level": "error",
      "code": "dangling-ref",
      "message": "ref 'nope' matches no entry id/guid or sense id",
      "file": "dictionary.lift",
      "entry_id": "apu",
      "guid": null,
      "line": 88
    },
    {
      "level": "warning",
      "code": "uri-not-rfc",
      "message": "<range href='file://C:/...'>: تم استخدام حرف محرك أقراص Windows كمرجع URI (بأسلوب FLEx file://C:/)",
      "file": "dictionary.lift",
      "entry_id": null,
      "guid": null,
      "line": 6
    }
  ],
  "summary": {
    "errors": 1,
    "warnings": 1,
    "allowed": 0
  }
}

$ sil-lift stats sango.lift
entries:   3507
senses:    4541
...

$ sil-lift export dictionary.lift --langs en,fr -o dictionary.csv
```

يتم إخراج جميع البيانات بتنسيق UTF-8، على جميع الأنظمة الأساسية وسواء تم إرسالها إلى وحدة التحكم أو عبر أنبوب أو إعادة توجيه `>` — ولا يتم أبدًا استخدام ترميز الإعدادات المحلية (cp1252 في نظام Windows، وASCII في الإعدادات المحلية لـ C/POSIX)، الذي لا يمكنه تمثيل محتوى LIFT. وبالتالي، فإن الأمر `sil-lift export dictionary.lift > dictionary.csv` يكتب بالضبط نفس البايتات التي يكتبها الأمر `-o dictionary.csv`، بما في ذلك علامات نهاية الصفوف CRLF.

رموز الخروج: `0` نجاح (التحذيرات لا تؤدي إلى فشل التشغيل ما لم يتم استخدام الخيار `--strict`)، `1` نتائج (أخطاء في التحقق من الصحة / وسائط مفقودة أو بها أخطاء إملائية / تحذيرات عند استخدام الخيار `--strict`، دون احتساب الرموز الممنوحة لخيار `--allow`)، `2` فشل في الإدخال/الإخراج في أي من الطرفين — إدخال لا يمكن قراءته، أو إخراج لا يمكن كتابته (مثل قيام قارئ مثل `head` بإغلاق الأنبوب، أو امتلاء القرص).
