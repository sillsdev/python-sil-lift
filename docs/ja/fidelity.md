# フィデリティの保証

LIFTは_相互運用_フォーマットであるため、最初のルールは**理解できないものは決して削除しない**ことです。 `sil-lift`の契約。これは、実行のたびにテストスイートによって検証されます（コーパスファイルおよびプロパティベースの生成）。

## 読書

正しく構成された LIFT 0.13 ドキュメントであれば、スキーマに違反するコンテンツが含まれていても読み込まれます。モデルで定義されていないものはすべて、最も近いノードの不透明な `Extras` コンテナに _LIFT 残余_ として格納されます。これは FieldWorks が同じ概念に対して用いる名称であり、`LiftResidue` フィールドに保存されます。これには、未知の属性や要素、XML コメントや処理命令、不要なテキスト、および形式不備の型付き属性などが含まれます （不正な日付は、`Extras`内に元の文字列のまま残され、型付きフィールドは`None`となります）。

## 変更のない文書を保存する

編集を行わずに `load()` → `save()` を実行すると、**バイト単位で同一の出力**が生成されます。つまり、再フォーマット、再エスケープ、順序の変更は行われず、バイト順マークやXML宣言も含まれます。現在、正規化リストは存在しません。恒等式は厳密です。タイムスタンプはコンテンツから生成されるため、変更されていないドキュメントにはタイムスタンプも生成されません。

例外（ライターは完全なカノニカルシリアライゼーションにフォールバックします。これは意味的には完全ですが、バイト単位の整合性は保たれません）：

- ソースのエンコーディングがASCII互換ではない（UTF-8/US-ASCIIではない）、または
- ソースにDOCTYPEが含まれているか、または
- バイトスキャナとパーサーの間で、ドキュメントの最上位構造に関する認識に相違がある。例えば、仕様外の2つ目の `<header>` がある場合、パーサーはこれを1回だけ保持するが（スキャナは意図的に保守的であり、疑わしい場合はソースバイトを一切取得しない）、あるいは
- ソースはファイルから読み込まれるのではなく、メモリ上で構築されました。

## 編集したドキュメントの保存

- **変更されていないエントリは、元のバイト列そのままが出力されます。** エントリのモデルオブジェクトのいずれかの部分が parse 以降に変更された場合、そのエントリは変更済みとみなされます（これは、ダーティフラグではなく、正規シリアライゼーションのスナップショットによって検出されます）。
- **選択されたエントリは、正規形式で完全に再シリアライズされます。** 正規形式は以下の通りです：
  - UTF-8。
  - 混合コンテンツの_外側_では2スペースのインデントが適用されますが、`<text>` および `<span>` 内の空白は一切変更されません。
  - 要素ごとに文書化された子要素のグループ。`<entry>` の場合：lexical-unit、citation、pronunciations、variants、senses、notes、relations、etymologies、annotations、traits、fields。
  - 属性の順序を修正しました。
  - ISO-8601形式の日付（UTCの場合は`Z`）。
- **残りのデータはすべて再出力されます。** その位置は元の子インデックスに戻され、新しい子リストに合わせてクリップされます。ただし、これは近似処理であり、正確なバイト位置が保証されるのは変更されていないエントリのみです。
- エントリの追加、削除、または順序変更を行うと、ドキュメント構造は再シリアル化されますが、変更されていないエントリのバイトデータはすべてそのまま出力されます。
- **更新されたエントリには**、新しい `dateModified` が記録され、`dateCreated` が存在しない場合はそれが追加されます。詳しくは、[生成されるタイムスタンプ](#generated-timestamps) を参照してください。

!!! note "&quot;ここでいう「Canonical&quot; 」は、他のどのCanonical XMLとも関係ありません。"
    このページにおける「標準形」とは、上記の箇条書きで説明されている、`sil-lift`独自の文書化された形状を指します。これは、W3CのCanonical XML（C14N）プロセスとは無関係です。これは、`SIL.Core` の `CanonicalXmlSettings` クラスとは無関係です。

## 生成されたタイムスタンプ

生成されたスタンプは、出力の中で唯一、入力に依存しないものです。

- **スタンプが押される対象**。読み込まれた後に内容が変更されたすべてのエントリ。これらは新しい `dateModified` が設定され、もし `dateModified` が存在しない場合は、その時点と同じ `dateCreated` が設定されます。読み込み日以前に配信された編集内容は、その属性に基づいて照合を行うすべてのシステム（FieldWorksやThe CombineのLIFTインポートを含む）からは、変更されていないように見えます。
- **エントリのみ。** `<entry>` の下にはノードを置かず、ヘッダーには何も記述しないこと。
- **そのまま残されるもの。** 呼び出し元が意図的に日付を設定したエントリ、およびロード後に作成され、すでに日付が設定されているエントリ。
- **日付のクリアは有効です。** `date_modified` が設定されたエントリを読み込んだ際に `entry.date_modified = None` とすると、これは他の値と同様に意図的な設定であるため、コンテンツが変更されたかどうかに関わらず、そのエントリは `dateModified` なしで出力されます。それがない状態で読み込まれたエントリの場合は事情が異なります。そこでは `None` がすでに値として設定されており、フィールドに一度も触れていない場合と見分けがつかないため、編集を行っても依然としてスタンプが押されます。
- **解析できない日付は置き換えられます。** モデルが解析できなかった日付は、日付ではなく [残余](#reading) となるため、スタンプによって上書きされ、元の文字列は削除されます。編集されたエントリには、`dateModified="whenever"` とするよりも、実際の日付を記載した方が望ましいです。
- **その瞬間。** 秒単位の精度でのUTC（`YYYY-MM-DDTHH:MM:SSZ`、FieldWorksのエクスポートデータで採用されている形式）、壁掛け時計から読み取った時刻。 1秒には1つの日付が含まれるため、前回の編集から1秒以内に保存された編集には、同じタイムスタンプが付与されます。
- **`save(when=...)`** は、実時間ではなく「瞬間」を指定します。これにより、diff ベースの CI ゲートにおいて、タイムスタンプ付きの出力を再現可能に保つことができます。タイムゾーンに対応している必要があり、UTCの整数秒に正規化されている。
- **`save(stamp=False)`** は、残差を含め、モデルをその時点の状態のまま正確に書き出します。
- **`.lift` 書き込みによるコミットのスタンプ付け。** その書き込みが反映されるのを妨げる要因があれば、日付は元に戻ります。一度着地すれば、たとえその後で別の書き込みが失敗しても、それらはそのまま残ります。

## コンテンツXMLでは表現できない

BMP以外の文字（絵文字、CJK拡張B、アドラム文字、および U+FFFF より上のすべての文字）は通常のコンテンツとして扱われ、往復でバイト単位で同一に保持されます。「サロゲートペア」はUTF-16のエンコーディングに関する詳細です。Pythonの文字列はコードポイントのシーケンスであるため、リーダー、バイトスキャナー、ライターのいずれにおいても、サロゲートペアが実際に処理されることはありません。

_単独の_代理（U+D800–U+DFFF）の場合は異なります。Pythonの文字列には1つを含めることができますが、XMLドキュメントには、どのエンコーディングであっても含めることはできません。ファイルからは決して取得できません。パーサーは、`&#xD800;` という文字参照や CESU-8/WTF-8 バイトといった両方の表記を拒否し、API を通じて割り当てられた文字列からのみ取得可能です。このようなモデルを保存すると、ノード名とコードポイント名を指定した `LiftWriteError` が発生し、何も書き込まれません。スキーマ層によるチェックを行うためにドキュメントをシリアル化できないため、検証ではこれが単一の `lone-surrogate` エラーとして報告されます。

## 既知の近似値（接触したノードのみ）

- `<text>` の実行の `内部` にあるコメントは保持されますが、正確な文字オフセットの位置には残されず、その実行の隣に移動されます。
- 編集対象の要素内におけるクロス型の子要素の順序は、正規のグループ化に正規化されます（LIFTスキーマの `interleave` により、この順序は意味的に無意味となります）。
- `lang` 属性のない `<form>` または `<gloss>` は再発行されず、そこに含まれていた要素も同様に再発行されません。検証では、この省略が `form-missing-lang` として報告されます。変更されていないノードはソースバイトを保持するため、そのエントリ内の何かが編集されるまでは、この形式が維持されます。
- 存在はするが、フォームも残留物も一切含まないマルチテキスト要素（例：`<definition></definition>`）は、再出力されません。このモデルでは、これらのフィールドを常に存在する `Multitext` として表現しています（`lexical-unit`、`citation`、`definition`、関係の `usage`、およびヘッダーの `label` / `abbrev` / `description`）として常に存在する `Multitext` として表現しているため、解析後は空の `Multitext` と存在しない `Multitext` を区別することができません。意味的な情報は一切失われません。
