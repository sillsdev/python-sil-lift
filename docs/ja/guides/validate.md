# 検証

検証は常に明示的に行われます。読み込みや保存の際、暗黙的に検証が行われることはありません。

```python
import sil_lift

# 網羅的：Problem（スキーマ＋セマンティック層）の遅延ストリーム。
for problem in sil_lift.iter_problems("dictionary.lift"):
    print(problem)
    # エラー [dangling-ref] dictionary.lift:88 (entry apu): ref 'nope' が ... と一致します

# フェイルファースト：最初のエラーレベルの問題で停止する。
if any(p.level == "error" for p in sil_lift.iter_problems("dictionary.lift")):
    raise SystemExit(1)

# メモリ内状態（最初にシリアライズされる。大規模な辞書では、ドキュメントに記載されているようにコストがかかる）：
lex = sil_lift.load("dictionary.lift")
problems = list(lex.iter_problems())
```

各 `Problem` には、`level`（`"error"`/`"warning"`）、一意の `code`、`message`、およびその問題に関するアドレス情報が含まれます。

- `file`: レキシコンにパスがない場合は `None`。
- `entry_id`：発見内容が1つのエントリに関する場合に設定します。
- `guid`：対象となるオブジェクト（エントリまたは範囲要素）にguidが存在する場合に設定されます。
- `line`：検索結果が文書内の行に対応する場合に設定します。

範囲に関する結果は、その範囲を定義する `.lift-ranges` コンパニオンに対して返され、エントリは含まれません。設定されていないフィールドは `None` です（`--format json` では `null` となります。この形式では、すべてのキーが常に存在します）。

## レイヤー

1. **LIFTスキーマ**（`lift-0.13.rng`、LIFT 0.13のRELAX NG文法。lift-standardからバイト単位で同一の形でベンダー提供されている）が`.lift`ファイル上に定義されています。
2. **Rangesスキーマ**（`lift-ranges-0.13.rng`、lift-standardからもベンダーとして提供されている）は、追跡対象のすべての `.lift-ranges` コンパニオンを対象としており、`.lift` ではなくコンパニオンを宛先としています。
3. **スキーマでは表現できないセマンティックチェック**：13件あり、それぞれ1つのコードが割り当てられている。

## 問題コード

各検出結果には、それがどのレイヤーで生成されたかに関わらず、以下のいずれかが含まれます。「schema」と「uri-not-rfc」はスキーマ・レイヤーに由来するもので、その他はセマンティックチェックの結果です。 `missing-id` を除き、すべてのコードはデフォルトでチェックされます。`missing-id` はオプション機能であり、有効にするには `require_ids=True`（または `--require-ids`）を指定してください。コードは安定しているため、スクリプトでそれらを照合することができます。 `--strict` を指定すると、すべての警告がエラーとして扱われます。 `sil-lift validate --allow CODE` を実行すると、そのコードは合格・不合格の判定対象から除外されます。

| コード                      | レベル | 何がフラグとして表示されるか                                                                          |
| ------------------------ | --- | --------------------------------------------------------------------------------------- |
| `ambiguous-ranges-file`  | 警告  | ケースフォールディングおよびNFCの条件下で、1つのコンパニオン名に対応する複数のファイル                                           |
| `dangling-ranges-href`   | 警告  | ヘッダー `range/@href` が、対応するファイルが見つからない状態になっている                                            |
| `dangling-ref`           | エラー | エントリや意味に一致する `relation/@ref` または `variant/@ref` がない                                     |
| `duplicate-form-lang`    | 警告  | 1つのマルチテキスト内に、同じ言語を使用する2つのフォーム                                                           |
| `duplicate-guid`         | エラー | エントリ間で、あるいは1つのドキュメント内の範囲／範囲要素間で再利用されるGUID                                               |
| `form-missing-lang`      | エラー | `<form>` または `<gloss>`。ただし、スキーマで必須とされる `lang` は含まれていません。                                |
| `media-href-mismatch`    | 警告  | 大文字小文字の区別を無視するモード（case folding）またはNFCの場合にのみ、そのファイルにアクセスできるmedia href                    |
| `missing-id`             | エラー | **[opt-in]** GUID がないエントリ、ID がないセンス |
| `missing-media`          | 警告  | 参照先の音声ファイルまたは画像ファイルがディスク上にありません                                                         |
| `正規化の不一致`                | 警告  | NFCでのみ、そのIDを参照するIDに到達する名前                                                               |
| `range-parent`           | エラー | `range-element/@parent` には、兄弟要素の ID が定義されていない                                           |
| `スキーマ`                   | エラー | `.lift` ファイルまたはコンパニオン内で、RELAX NG 文法違反が発生しています                                           |
| `未定義の範囲値`                | 警告  | 文法情報または範囲キー付き形質値のうち、その範囲にリストされていないもの                                                    |
| `unreadable-ranges-file` | 警告  | 存在はするが、読み取り可能な範囲ドキュメントではないコンパニオン候補                                                      |
| `uri-not-rfc`            | 警告  | 有効なURIではないhref（FLExの `file://C:/...`）                                                   |

### 検証で何が確認されるか

3つのレイヤーはすべて、そのままシリアライズされたドキュメントに基づいて動作するため、まったくシリアライズできないドキュメントについては、代わりに単一の `lone-surrogate` エラーとして報告されます。「フィデリティの保証」[こちら](../fidelity.md#content-xml-cannot-represent)をご覧ください。

検証結果は読み取り専用です。これは、保存によって `dateModified` が設定される前の、その時点でのドキュメントの状態を報告するものです。スタンプによってエラーが発生することはないため、検証に合格したドキュメントは、保存後も引き続き有効となります。

### コンパニオンフォルダのコード

複数のファイルに一致するコンパニオン名は、それらのファイルを一切読み込みません。1つを除いてすべてが名前変更または削除されるまで、それらが定義する範囲は存在しなくなります。

3つのコンパニオン・フォルダ・コード（`ambiguous-ranges-file`、`dangling-ranges-href`、および`unreadable-ranges-file`）は、コンパニオン検出が実行された場合にのみ報告されます：

- `resolve_ranges=False` を指定して読み込むと、コンパニオンがスコープ外となるため、いずれも報告されません。
- 後で `add_ranges_file()` を使ってファイルを追加しても、これらのコードが参照しているフォルダは読み込まれないため、それらは復元されません。

`resolve_ranges=False` は、`missing-media` や `media-href-mismatch` には影響しません。メディアはモデルに解決されることがないため、除外すべき対象が存在しないからです。

### メディアコード

sil-lift は、指定された href のほか、`audio/`（発音用メディア）や `pictures/`（イラスト）の下にも、各メディアファイルを探します。そのフォルダ名は sil-lift 自身の推測であり、ドキュメントに記載されているものではないため、大文字小文字の区別を問わず一致し、そのスペルについては一切報告されません。

`missing-media` と `media-href-mismatch` は、メディアのチェックをそれぞれ分担しています。前者は、href に指定されたファイル名がどのようなスペルであっても該当するファイルが見つからなかった場合を指し、後者は、該当するファイルは見つかったものの、href の指定とファイル名が完全に一致しなかった場合を指します。 2つ目は、ポータビリティに関する発見です。ファイルはここにあるにもかかわらず、このフォルダを公開しているホストが大文字と小文字を区別する場合、そのファイルは見つかりません。

スペルミスのある「_folder_」は、参照数がいくつあろうと、名前変更は1回分として扱われるため、1回だけ報告され、エントリは作成されません。参照ごとに、スペルミスのある_ファイル名_が報告され、それを記述したエントリに対して通知されます。

## 実環境におけるFieldWorks（FLEx）の出力結果

FieldWorksは、厳格なツールによって拒否されるようなコンテンツを体系的に生成してしまう。実際の辞書が有用に検証されるよう、sil-liftの方針は以下の通りです：

- `file://C:/...` という href（無効な URI）は、スキーマエラーではなく**警告**（`uri-not-rfc`）として報告されます。C# バリデータはこれらを拒否したことはありません。
- 法的にインターリーブされた子要素（ある意味では `field, note, field, note` など）にはフラグが立てられません。これにより、libxml2 における誤検知が無視されます。
- `range-element` 内の FLEx の `trait`/`field` 拡張は、**報告される**（range スキーマに対するスキーマエラーとして）：これらは紛れもない仕様からの逸脱である。
- 名前は、Unicodeの**NFC正規化**に基づく範囲および範囲要素の`id`に対して解決されます。対象となるのは、`parent`リンク、範囲値、および範囲のキーとなる`trait`名またはヘッダーの`range` IDです。
  - FLExはエクスポート時にNFCに正規化されますが、一部の書き込みではその処理をバイパスしていたため、範囲要素の`id`がNFDである一方で、そのラベル、自身の`parent`、およびそれを指定する`.lift`の値がNFCとなっている場合があります。
  - 厳密に比較すると、この点について2つの点で誤りとなる。 NFD ID への参照は、エクスポート自体は問題がないにもかかわらず、破損していると報告される可能性があります。また、`id` が NFD である範囲はチェックの対象外となります。つまり、それに一致するトレイト名が存在しないため、どの範囲とも一致しないトレイト名はそのまま受け入れられます。
  - 正規化を行って初めて一致した名前は、`normalization-mismatch` **警告** として報告されます。この警告は、参照ごとではなく ID ごとに 1 回、その名前を定義しているファイルに対して発行されます。データ自体は正しいのですが、生の文字列を比較するだけのユーザーでは、それらの参照を解決することはできません。
  - IDは決して書き換えられません。ファイルには、元のスペルがそのまま保持されます。
