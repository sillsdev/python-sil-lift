# 検証

検証は常に明示的に行われます。読み込みや保存の際、暗黙的に検証が行われることはありません。

```python
import sil_lift

# 網羅的：Problem（スキーマ層＋セマンティック層）の遅延ストリーム。
for problem in sil_lift.iter_problems("dictionary.lift"):
    print(problem)
    # エラー [dangling-ref] dictionary.lift:88 (entry apu): ref 'nope' matches ...

# フェイルファースト：最初のエラーレベルの問題で LiftValidationError を発生させます。
sil_lift.validate_file("dictionary.lift")

# メモリ内状態（最初にシリアライズされる — 大規模な辞書では、ドキュメントに記載されているようにコストがかかる）：
lex = sil_lift.load("dictionary.lift")
problems = list(lex.iter_problems())
```

各 `Problem` には、`level`（`"error"`／`"warning""`）、一意の `code`、`message`、および検出結果に関連するアドレス情報が含まれます： `file`（レキシコンにパスがない場合は`None`）、特定のエントリに関連する場合は`entry_id`、対象となるオブジェクト（エントリまたは範囲要素）に一意の識別子がある場合は`guid`、ドキュメント内の行に対応する場合は`line`。 範囲に関する結果は、その範囲を定義する `.lift-ranges` コンパニオンに対して返され、エントリは含まれません。 設定されていないフィールドは `None` となります。`--format json` では `null` となり、すべてのキーが常に存在します。

## レイヤー

1. **RELAX NG** による LIFT 0.13 文法との照合（lift-standard からベンダー提供されたもの — 本パッケージにコミットされたバイト単位で同一のコピー）。
2. **Rangesスキーマ** — 本プロジェクトの `lift-ranges-0.13.rng` — は、追跡対象となっているすべての `.lift-ranges` コンパニオンに対して適用され、`.lift` ではなくコンパニオンを宛先としています。
3. **文法では表現できないセマンティックチェック** — 計10項目、それぞれ1つのコード。

## 問題コード

各検出結果には、それがどのレイヤーで生成されたかにかかわらず、これらのいずれかが含まれます。`schema` と `uri-not-rfc` はスキーマ・レイヤーからのもので、残りの10個はセマンティックチェックによるものです。 文字列はサポートされているインターフェースです。`--strict` を指定すると、すべての警告がエラーとして扱われます。

| コード                     | レベル | 何がフラグとして表示されるか                                      |
| ----------------------- | --- | --------------------------------------------------- |
| `ambiguous-ranges-file` | 警告  | ケースフォールディングおよびNFCの条件下で、1つのコンパニオン名に対応する複数のファイル       |
| `dangling-ranges-href`  | 警告  | ヘッダー `range/@href` が、対応するファイルが見つからない状態になっている        |
| `dangling-ref`          | エラー | エントリや意味に一致する `relation/@ref` または `variant/@ref` がない |
| `duplicate-form-lang`   | 警告  | 1つのマルチテキスト内に、同じ言語を使用する2つのフォーム                       |
| `duplicate-guid`        | エラー | エントリ間で、あるいは1つのドキュメント内の範囲／範囲要素間で再利用されるGUID           |
| `missing-id`            | エラー | `require_ids` によるオプトイン：GUID のないエントリ、ID のないセンス       |
| `missing-media`         | 警告  | 参照先の音声ファイルまたは画像ファイルがディスク上にありません                     |
| `正規化の不一致`               | 警告  | NFCでのみ、そのIDを参照するIDに到達する名前                           |
| `range-parent`          | エラー | `range-element/@parent` には、兄弟要素の ID が定義されていない       |
| `スキーマ`                  | エラー | `.lift` ファイルまたはコンパニオン内で、RELAX NG 文法違反が発生しています       |
| `未定義の範囲値`               | 警告  | 文法情報または範囲キー付き形質値のうち、その範囲にリストされていないもの                |
| `uri-not-rfc`           | 警告  | 有効なURIではないhref — FLExの `file://C:/...`              |

3つのレイヤーはすべて、`save()` が書き込む内容を基に動作するため、まったくシリアライズできないドキュメントについては、代わりに単一の `lone-surrogate` エラーとして報告されます。詳細は [忠実度の保証](../fidelity.md#content-xml-cannot-represent) を参照してください。

複数のファイルに一致するコンパニオン名は、それらのファイルを一切読み込みません。1つを除いてすべてが名前変更または削除されるまで、それらが定義する範囲は存在しなくなります。

## 実環境におけるFieldWorks（FLEx）の出力結果

FieldWorksは、厳格なツールによって拒否されるようなコンテンツを体系的に生成してしまう。 実際の辞書が有用に検証されるよう、sil-liftの方針は以下の通りです：

- `file://C:/...` という href（無効な URI）は、スキーマエラーではなく**警告**（`uri-not-rfc`）として報告されます。C# バリデータはこれらを拒否したことはありません。
- 法的に交互に配置された子要素（ある意味では `field, note, field, note` など）にはフラグが付けられず、これにより libxml2 における誤検知を回避しています。
- `range-element` 内の FLEx の `trait`/`field` 拡張は、**報告される**（range スキーマに対するスキーマエラーとして）：これらは紛れもない仕様からの逸脱である。
- 名前は、Unicodeの**NFC正規化**に基づく範囲および範囲要素の`id`に対して解決されます。これには、`parent`リンク、範囲値、および範囲を識別する`trait`名またはヘッダーの`range` IDが含まれます。 FLExはエクスポート時にNFCに正規化されますが、一部の書き込みではその処理をバイパスしていたため、範囲要素の`id`がNFDである一方で、そのラベル、自身の`parent`、およびそれを指定する`.lift`の値がNFCとなっている場合があります。
  - 厳密に比較すると、正常なエクスポートは不正なように見えます。また、`id` の綴りが逆になっている範囲は、まったくチェックされません。これは、どの範囲にも到達しないトレイト名は、何の警告もなく受け入れられるためです。
  - 正規化を行って初めて一致した名前は、`normalization-mismatch` **警告** として報告されます。この警告は、ID ごとに、参照の不一致がいくつあっても 1 回のみ発行され、その名前を定義しているファイルに対して通知されます。 データ自体は正しいのですが、生の文字列を比較するだけのユーザーでは、それらの参照を解決することはできません。
  - IDは決して書き換えられません。ファイルには、元のスペルがそのまま保持されます。
